# 5 Тестування та оцінка ефективності

## 5.1 Підхід до формування доказової бази

Оскільки створення повного власного датасету для 10 статичних і 3 динамічних жестів потребує
значного часу, у роботі використано комбіновану схему оцінювання. Основою кількісного аналізу
є відкриті набори даних HaGRID/HaGRIDv2, IPN Hand, Jester та, за наявності доступу, NVGesture
\cite{kapitanov2024hagrid,nuzhdin2024hagridv2,benitez2021ipnhand,materzynska2019jester,molchanov2016online}.
Додатково передбачено малий власний контрольний набір для жестів, які не мають точного відповідника
у відкритих наборах, зокрема `INDEX_LEFT`, `INDEX_RIGHT` і `CIRCLE`.

Відкриті датасети використовуються не для зміни цільового словника жестів, а для відтворюваної
оцінки реалізованого pipeline: детектування руки, класифікації, debouncing, формування команд,
затримки та частоти кадрів. Усі результати розділяються за джерелами даних, щоб не змішувати
різні домени зйомки та не робити завищених висновків щодо узагальнення системи.

## 5.2 Набори даних

Для статичних жестів основним джерелом є HaGRIDv2, оскільки він містить велику кількість
RGB-зображень, розмітку жестів, bounding boxes, `user_id` для коректного поділу за суб'єктами та
автоматично анотовані hand landmarks \cite{nuzhdin2024hagridv2}. Для HRI-контексту як додатковий
малий набір може використовуватися HANDS, що містить RGB-D кадри статичних жестів для
людино-роботної взаємодії \cite{nuzzi2021hands}.

Для динамічних жестів використовуються IPN Hand і Jester. IPN Hand містить continuous RGB-відео
з non-gesture сегментами, тому підходить для оцінки false positives та роботи алгоритму у
потоці кадрів \cite{benitez2021ipnhand}. Jester містить короткі кліпи жестів, серед яких є
класи `Shaking Hand`, `Pulling Hand In`, `Swiping Left`, `Swiping Right`, `Thumb Up`,
`Thumb Down` і `Stop Sign`, що дає змогу перевірити частину динамічного та статичного словника
\cite{materzynska2019jester}. NVGesture розглядається як опційне джерело для рухів обертання
та push-pull, якщо доступ і ліцензійні умови буде підтверджено перед експериментом
\cite{molchanov2016online}.

У прототипі підключено IPN Hand як сегментований benchmark: анотації `t_start`/`t_end`
перетворюються у manifest-рядки з межами кадрів. Для першого запуску використано 90 сегментів
тестового split: 30 сегментів `WAVE_LR`, 30 сегментів `PULL_TOWARD` та 30 non-gesture
сегментів `UNKNOWN` для оцінки помилкових спрацювань.

## 5.3 Метрики

Оцінювання виконується за такими метриками:

- accuracy, precision, recall та macro-F1 для статичних і динамічних жестів;
- confusion matrix для аналізу помилок між схожими класами;
- latency від отримання кадру до формування `RobotCommand`;
- FPS pipeline на CPU;
- false-positive rate для критичної команди `EMERGENCY_STOP`;
- частка кадрів або вікон, для яких рука не була знайдена та результатом став `UNKNOWN`.

Для статичних жестів цільовим орієнтиром є F1-score не нижче 90% за нормального освітлення, для
динамічних - не нижче 80%. Для критичної команди `EMERGENCY_STOP` окремо перевіряється, що
false-positive rate не перевищує 5%.

Перший baseline на IPN Hand показав macro-F1 0.487 для підмножини з двох динамічних жестів
і non-gesture сегментів. Середня затримка обробки становила 56.4 ms, середня частота -
21.5 FPS на локальному CPU. Результат не досягає цільового F1 для динамічних жестів, але
показує працездатність pipeline на реальних continuous-відео та визначає напрям подальшого
налаштування порогів динамічного класифікатора.

Після запису власного контрольного набору `own_control` було навчено легкі `ExtraTrees`-моделі
для статичних landmark-ознак і динамічних trajectory-ознак. На calibrated-прогоні по 101
записаному відео macro-F1 підвищився з 0.130 для rule-based baseline до 0.976 для гібридної
моделі; weighted-F1 становив 0.969, accuracy - 0.950, а false-positive rate для критичної
команди `EMERGENCY_STOP` - 0.0. Для перевірки узагальнення додатково виконано hold-out split:
77 відео для навчання і 24 відео для тестування. На відкладеному наборі отримано accuracy
0.750, macro-F1 0.769 і weighted-F1 0.758. Отже, гібридна модель значно покращує роботу на
телефонних відео, але для досягнення цільового F1 на незалежному наборі потрібне розширення
датасету або додаткові записи від інших операторів.

Для відтворюваного підрахунку метрик додано скрипт `scripts/benchmark.py`. Він приймає CSV
з очікуваними та передбаченими жестами, формує aggregate summary, per-class F1 і confusion
matrix. Для візуалізації результатів використовується `scripts/plot_results.py`, який генерує
графіки macro-F1, F1 за жестами, runtime-показники та матрицю помилок.

Щоб перетворити subset датасету у такий CSV, використовується `scripts/evaluate_manifest.py`.
Вхідним файлом є manifest з колонками `path`, `expected_gesture`, `media_type`, `dataset`,
`condition` і `distance`. Для зменшення ручної роботи додано `scripts/build_manifest.py`, який
сканує локальні class-named директорії та формує manifest для `own_control`, HaGRID/HaGRIDv2,
Jester або IPN Hand. Для швидкого збирання малого контрольного набору передбачено
`scripts/record_test_video.py`, який записує короткі кліпи у `data/external/own_control/`.
Скрипт оцінювання підтримує зображення, відео та JSON-файли з послідовностями MediaPipe
landmarks, тому один формат може використовуватися для HaGRIDv2, Jester, IPN Hand і малого
контрольного набору.

## 5.4 Обмеження експерименту

Відкриті набори даних не повністю відтворюють умови роботи мобільного робота: камера, фон,
дистанція, інструкції до жестів і роздільна здатність можуть відрізнятися. Тому результати на
HaGRIDv2, IPN Hand і Jester інтерпретуються як відтворювана алгоритмічна оцінка, а не як повний
доказ готовності до експлуатації. Практична працездатність підтверджується окремим демо-сценарієм,
у якому камера передає кадри до pipeline, gesture classifier формує команду, а sender записує її
в лог або передає на робототехнічну платформу.

## 5.5 Аналітичне оцінювання UX-рішень

Окремо виконано аналітичне оцінювання користувацької взаємодії для словника з 13 жестів.
Кожен жест оцінено за чотирма критеріями: семантична відповідність команді, ергономічне
навантаження, ризик випадкового спрацювання та потреба у візуальному фідбеку. Оцінювання
показало, що найбільш природними для оператора є `OPEN_PALM` для `STOP`, `THUMB_UP` для
`START`, напрямні жести `INDEX_LEFT`/`INDEX_RIGHT` для поворотів, `OK_SIGN` для підтвердження
та `CIRCLE` для обертання.

Найвищу потребу у додатковому фідбеку мають критичні та динамічні команди: `EMERGENCY_STOP`,
`CONFIRM_ACTION`, `WAVE_LR`, `CIRCLE` і `PULL_TOWARD`. Для них у прототипі доцільно показувати
не лише назву розпізнаного жесту, а й стан debouncing, confidence та факт передавання команди
у sender. Жести `PEACE`, `THREE_FINGERS` і `PINKY` мають нижчу семантичну очевидність, тому
вони потребують короткої навчальної підказки або демонстраційного overlay.

За результатами оцінювання сформовано такі UX-вимоги:

- поточний жест і підтверджена команда мають відображатися окремо;
- для спеціальних і динамічних команд потрібні підвищені пороги підтвердження;
- debug overlay має містити gesture, command, confidence, handedness і debounce progress;
- адаптивне калібрування потрібно пропонувати перед роботою нового користувача;
- command log має зберігати послідовність сформованих команд для аналізу помилок.
