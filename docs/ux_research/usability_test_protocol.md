# Протокол usability test

## Мета

Перевірити, чи може користувач виконувати базові сценарії керування мобільним роботом
за допомогою жестів, і чи покращує UX-фідбек розуміння стану системи.

## Умови тестування

Тест бажано проводити у двох режимах:

- A: без розширеного UX-фідбеку, тільки команда в логах або мінімальний текст;
- B: з UX-фідбеком: поточний жест, confidence, індикатор підтвердження, команда.

Якщо часу мало, можна провести тільки режим B і чесно описати, що A/B-порівняння не
виконувалося.

## Завдання для учасника

1. Зупинити робота жестом `OPEN_PALM`.
2. Запустити рух вперед жестом `FIST`.
3. Повернути робота ліворуч.
4. Повернути робота праворуч.
5. Змінити швидкість.
6. Підтвердити дію жестом `OK_SIGN`.
7. Виконати аварійну зупинку.
8. Виконати один динамічний жест: `WAVE_LR`, `CIRCLE` або `PULL_TOWARD`.

## Метрики спостереження

Для кожного завдання фіксуються:

- task_id;
- participant_id;
- mode: `A` або `B`;
- success: так/ні;
- time_to_command_seconds;
- attempts;
- false_commands;
- participant_comment;
- observer_notes.

## Післятестова анкета

Після виконання завдань учасник заповнює:

- SUS;
- коротку NASA-TLX;
- Borg CR10 для втоми руки;
- 3 відкриті питання:
  - Що було найбільш зрозумілим?
  - Що викликало плутанину?
  - Який жест ви б змінили?

## Критерії успішності

Мінімальні цілі для дипломної роботи:

- task completion rate >= 85%;
- середня кількість спроб <= 2;
- SUS >= 70 для прийнятної зручності, бажано >= 80;
- відсутність хибних спрацювань для `EMERGENCY_STOP`;
- учасники розуміють, коли система ще тільки розпізнає жест, а коли вже виконала команду.

## План аналізу

1. Порахувати середній час виконання завдання.
2. Порахувати task completion rate.
3. Порахувати середню кількість спроб.
4. Порівняти режим A і B, якщо обидва проводилися.
5. Виділити 3-5 основних UX-проблем.
6. Описати зміни, які внесено або заплановано після тестування.
